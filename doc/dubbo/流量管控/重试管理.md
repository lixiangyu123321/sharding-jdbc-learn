### 一、Dubbo重试的核心逻辑
Dubbo的重试是**消费端行为**：当服务调用出现「超时/网络异常/服务不可用」时，消费端会自动重新调用**其他服务端实例**（而非同一实例），核心目的是**提升读操作的成功率**，但对写操作有数据重复风险。

#### 关键前提
1. **重试触发条件**：仅对「非业务异常」触发，包括：
    - 调用超时（`TimeoutException`）
    - 网络异常（`NetworkException`）
    - 服务端连接失败（`ConnectException`）
    - 服务端线程池满（`ThreadPoolExhaustedException`）
      ❌ 不会触发重试的异常：业务自定义异常、服务端返回的`RpcException`（如参数错误）、幂等性已保证的异常。
2. **重试范围**：Dubbo会通过负载均衡选择**集群中其他可用实例**重试，不会重复调用同一实例（避免放大服务端压力）。
3. **总耗时计算**：总耗时 = 单次超时时间 × (重试次数 + 1)，例如：超时500ms + 重试2次 → 总耗时最多1500ms。

## 二、重试的配置方式（优先级与超时一致）
Dubbo重试通过`retries`参数配置，支持「全局/服务/方法」三级粒度，优先级：**方法级 > 服务级 > 全局级**，且**消费端配置优先于服务端**（服务端仅作为消费端未配置时的兜底）。

### 1. 代码注解配置（开发阶段）
#### 消费端（推荐，精准控制）
```java
// 1. 全局服务重试：该引用的所有方法重试1次
@DubboReference(version = "1.0.0", retries = 1)
private UserService userService;

// 2. 方法级精细配置：不同方法不同重试策略（推荐）
@DubboReference(version = "1.0.0", 
    methods = {
        @Method(name = "getUserById", retries = 1), // 读操作重试1次
        @Method(name = "addUser", retries = 0)       // 写操作禁用重试
    })
private UserService userService;
```

#### 服务端（兜底，消费端未配置时生效）
```java
@DubboService(version = "1.0.0", retries = 0) // 全局兜底禁用重试
public class UserServiceImpl implements UserService {
    // 方法级兜底（极少用）
    @Override
    public User getUserById(Long id) {
        return userMapper.selectById(id);
    }
}
```

### 2. 配置文件配置（生产静态配置）
#### SpringBoot YAML格式（推荐生产使用）
```yaml
dubbo:
  consumer:
    # 1. 全局重试：所有服务默认重试0次（核心！写操作兜底）
    retries: 0
    # 2. 服务级重试：覆盖全局，仅对该服务生效
    reference:
      com.example.dubbo.api.UserService:
        version: 1.0.0
        retries: 1 # 该服务所有方法默认重试1次
        # 3. 方法级重试：最细粒度，精准控制（生产首选）
        methods:
          getUserById: # 读操作：重试1次
            retries: 1
            timeout: 500 # 单次超时500ms，总耗时最多1000ms
          listUser: # 读操作：重试2次
            retries: 2
            timeout: 1000
          addUser: # 写操作：强制禁用重试（核心！）
            retries: 0
            timeout: 1000
  # 服务端兜底（消费端未配置时生效）
  provider:
    retries: 0
```

### 3. 动态配置中心（运行时调整，无需重启）
通过Nacos/Apollo/Dubbo Admin动态调整重试次数，实时生效（和超时动态配置逻辑一致）：
```yaml

      version: 1.0.0

```

### 4. API硬编码（特殊场景）
```java
// 构建消费端引用配置
ReferenceConfig<UserService> referenceConfig = new ReferenceConfig<>();
referenceConfig.setInterface(UserService.class);
referenceConfig.setVersion("1.0.0");
referenceConfig.setRetries(0); // 全局重试0次

// 方法级重试
Map<String, MethodConfig> methodMap = new HashMap<>();
MethodConfig methodConfig = new MethodConfig();
methodConfig.setName("getUserById");
methodConfig.setRetries(1);
methodMap.put("getUserById", methodConfig);
referenceConfig.setMethods(methodMap);

UserService userService = referenceConfig.get();
```

## 三、重试的适用场景与禁用场景（核心避坑）
### ✅ 建议开启重试的场景（读操作）
- 纯查询接口（如`getUserById`、`listUser`）：无数据修改，重试无副作用；
- 非核心统计接口：允许少量重复查询，优先保证可用性；
- 服务端偶发抖动（如网络闪断、线程池临时满）：重试可快速恢复。

### ❌ 必须禁用重试的场景（写操作/有状态操作）
| 禁用场景                | 风险示例                                  |
|-------------------------|-------------------------------------------|
| 新增数据（`addUser`）| 重试导致重复创建用户，数据冗余            |
| 修改数据（`updateUser`）| 重试导致数据被多次修改，版本混乱          |
| 删除数据（`deleteUser`）| 重试导致删除后再次删除，抛出不存在异常    |
| 涉及资金操作（`pay`）| 重试导致重复扣款，资金损失                |
| 调用第三方接口（如短信）| 重试导致重复发送短信，增加成本+用户投诉   |
| 有幂等性未保证的操作    | 任何修改数据且未做幂等的操作，均禁用重试  |

## 四、重试的高级配置与避坑要点
### 1. 重试次数的合理取值
- 读操作：建议`retries: 1`（最多2次调用），不建议>2次（会增加服务端压力，总耗时过长）；
- 核心读操作（如订单查询）：可设`retries: 1`，配合超时500ms，总耗时1000ms，兼顾成功率和响应速度；
- 非核心读操作：可设`retries: 0`，优先保证响应速度。

### 2. 重试与超时的配合（核心公式）
```
总最大耗时 = 单次超时时间 × (重试次数 + 1)
```
示例：超时500ms + 重试1次 → 总耗时最多1000ms，需确保总耗时不超过业务容忍的最大响应时间（如前端超时1500ms）。

### 3. 重试与负载均衡的配合
Dubbo重试时会通过负载均衡选择**其他实例**，推荐搭配：
- `loadbalance: random`（随机）：默认，重试时随机选其他实例；
- `loadbalance: leastactive`（最小活跃数）：优先选负载低的实例，重试成功率更高；
  ❌ 避免`loadbalance: roundrobin`（轮询）：可能重试到同一故障实例。

### 4. 重试与熔断/降级的配合
生产环境建议重试+熔断（如Sentinel/Dubbo原生熔断）搭配：
- 重试1次后仍失败 → 触发熔断，短时间内不再调用该服务，直接返回降级结果；
- 避免「重试风暴」：大量请求重试会压垮服务端，熔断可保护集群。

### 5. 幂等性处理（写操作特殊场景）
若写操作必须重试（极特殊场景），需先保证服务端接口**幂等**：
- 方案1：加幂等号（如请求ID），服务端校验ID是否已处理；
- 方案2：使用数据库唯一索引，重复插入时抛异常，消费端捕获后视为成功；
- 示例（服务端幂等处理）：
  ```java
  @Override
  public Boolean addUser(User user, String requestId) {
      // 1. 先查幂等号是否已处理
      if (idempotentMapper.exists(requestId)) {
          return true; // 重复请求，直接返回成功
      }
      // 2. 插入数据
      userMapper.insert(user);
      // 3. 记录幂等号
      idempotentMapper.insert(requestId);
      return true;
  }
  ```

## 五、重试的监控与问题排查
### 1. 重试日志排查
Dubbo会在INFO级别打印重试日志，关键词：`retry invoke`，示例：
```
INFO  [DubboClientHandler-192.168.1.100:20880-thread-1] - Retry invoke com.example.dubbo.api.UserService#getUserById, retry times: 1
```
通过日志可确认：是否触发重试、重试次数、重试的实例地址。

### 2. 监控指标
Dubbo会上报重试相关指标，可通过Dubbo Admin/Prometheus监控：
- `dubbo_consumer_retry_count`：重试次数；
- `dubbo_consumer_retry_success_count`：重试成功次数；
- `dubbo_consumer_retry_failure_count`：重试失败次数；
  设置告警：重试成功率<50% → 告警排查服务端问题。

## 六、生产最佳实践总结
### 核心配置模板（直接复用）
```yaml
dubbo:
  consumer:
    # 全局默认禁用重试（写操作兜底）
    retries: 0
    # 超时+重试配合：单次超时500ms，总耗时不超过1000ms
    timeout: 500
    reference:
      # 读操作服务配置
      com.example.dubbo.api.UserService:
        version: 1.0.0
        methods:
          # 读操作：重试1次
          getUserById:
            retries: 1
            timeout: 500
          # 写操作：强制禁用重试
          addUser:
            retries: 0
            timeout: 1000
  # 服务端兜底：禁用重试
  provider:
    retries: 0
    # 服务端超时兜底，避免消费端重试无意义
    timeout: 800
```

### 关键原则
1. **默认禁用，精准开启**：全局`retries: 0`，仅对确认安全的读操作开启重试；
2. **次数控制**：读操作重试≤1次，避免增加服务端压力；
3. **超时配合**：总耗时 = 单次超时 × (重试+1) ≤ 业务容忍时间；
4. **幂等优先**：写操作绝不重试，特殊场景需先做幂等；
5. **监控告警**：监控重试成功率，及时发现服务端故障。

### 总结
1. Dubbo重试是消费端行为，仅对非业务异常触发，优先选其他实例重试；
2. 配置优先级：方法级 > 服务级 > 全局级，消费端 > 服务端；
3. 读操作可开启1次重试，写操作必须禁用，特殊场景需保证幂等；
4. 重试需配合超时、负载均衡、熔断使用，避免重试风暴和数据不一致。
