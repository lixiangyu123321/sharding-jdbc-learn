# Provider 与 Consumer 模块依赖调整说明

## 调整目标

将所有运行时依赖（Web、JDBC、Dubbo、Sharding-JDBC、Spring Cloud Config 等）转移到 web 模块中，service 模块只包含业务逻辑代码。

## 调整原则

1. **Web 模块职责**：
   - 包含所有运行时依赖（Web、JDBC、Dubbo、Sharding-JDBC、Spring Cloud Config 等）
   - 包含启动类（Application）
   - 包含 Controller、DTO、VO、响应封装等 Web 层相关功能
   - 包含配置文件（application.yaml）

2. **Service 模块职责**：
   - 只包含业务逻辑代码（Service 实现类）
   - 不包含任何运行时依赖
   - 只依赖业务模块（facade、dao、common、integration）

3. **依赖关系**：Web 依赖 Service，Service 不依赖 Web（避免循环依赖）

## Provider 模块调整

### provider-web 模块

**职责**：
- 启动类（`ProviderApplication`）
- 配置文件（`application.yaml`）
- Controller（如果有 HTTP 接口）
- Request DTO
- Response VO
- 响应封装类

**依赖**：
```xml
- spring-boot-starter-web（Web 相关）
- spring-boot-starter-jdbc（数据库访问）
- spring-cloud-starter-config（配置中心）
- dubbo-spring-boot-starter（Dubbo 服务）
- dubbo-registry-nacos（注册中心）
- sharding-jdbc-spring-boot-starter（分库分表）
- provider-facade（接口定义）
- provider-common（公共模块）
- provider-dao（数据访问）
- provider-integration（第三方集成）
- provider-service（业务逻辑）
- lombok
```

**关键点**：
- ✅ 包含所有运行时依赖
- ✅ 包含启动类，可以扫描到所有依赖的模块
- ✅ Web 依赖 Service，可以调用 Service 中的业务逻辑

### provider-service 模块

**职责**：
- Dubbo 服务实现（`@DubboService`）
- 业务逻辑代码

**依赖**：
```xml
- provider-facade（接口定义）
- provider-common（公共模块）
- provider-dao（数据访问）
- provider-integration（第三方集成）
- lombok
```

**关键点**：
- ✅ 只包含业务逻辑，不包含运行时依赖
- ✅ 不依赖 Web 模块，避免循环依赖
- ✅ 纯业务代码，可以被 Web 模块调用

## Consumer 模块调整

```xml
- consumer-dao（数据访问）
- consumer-integration（第三方集成）
- consumer-service（业务逻辑）

```

**关键点**：
- ✅ 包含所有运行时依赖
- ✅ 包含启动类，可以扫描到所有依赖的模块
- ✅ Web 依赖 Service，可以调用 Service 中的业务逻辑
- ✅ Controller 中使用 `@DubboReference` 调用远程服务

### consumer-service 模块

**职责**：
- 业务逻辑代码

**依赖**：
```xml
- consumer-facade（Consumer 内部接口）
- consumer-common（公共模块）
- consumer-dao（数据访问）
- consumer-integration（第三方集成）
- lombok
```

**关键点**：
- ✅ 只包含业务逻辑，不包含运行时依赖
- ✅ 不依赖 Web 模块，避免循环依赖
- ✅ 纯业务代码，可以被 Web 模块调用

## 文件位置调整

### Provider

| 文件类型 | 原位置 | 新位置 | 说明 |
|---------|--------|--------|------|
| 启动类 | provider/service | provider/web | ✅ 启动类在 web 模块（包含运行时依赖） |
| Controller | - | provider/web | 如果有 HTTP 接口，放在 web 模块 |
| Dubbo 服务实现 | provider/service | provider/service | ✅ 保持不变（业务逻辑） |
| 配置文件 | provider/service | provider/web | ✅ 配置文件在 web 模块（启动类需要） |

### Consumer

| 文件类型 | 原位置 | 新位置 | 说明 |
|---------|--------|--------|------|
| 启动类 | consumer/service | consumer/web | ✅ 启动类在 web 模块（包含运行时依赖） |
| Controller | consumer/service | consumer/web | ✅ 在 web 模块 |
| 配置文件 | consumer/service | consumer/web | ✅ 配置文件在 web 模块（启动类需要） |

## 扫描包配置

### Provider

启动类在 `provider-web` 模块中，需要扫描所有模块：

```java
@SpringBootApplication
@EnableDubbo
public class ProviderApplication {
    // 默认扫描 org.lix.provider 包及其子包
    // 可以扫描到：
    // - provider-web 中的 Controller（如果存在）
    // - provider-service 中的服务实现
    // - provider-dao 中的 Mapper
    // - provider-integration 中的组件
}
```

### Consumer

启动类在 `consumer-web` 模块中，需要扫描所有模块：

```java
@SpringBootApplication
@EnableDubbo
public class ConsumerApplication {
    // 默认扫描 org.lix.consumer 包及其子包
    // 可以扫描到：
    // - consumer-web 中的 Controller
    // - consumer-service 中的业务逻辑
    // - consumer-dao 中的 Mapper
    // - consumer-integration 中的组件
}
```

## 优势

1. **职责清晰**：
   - Web 模块：包含所有运行时依赖和启动类，负责应用启动和 Web 层功能
   - Service 模块：纯业务逻辑代码，不包含运行时依赖

2. **依赖合理**：
   - Web 依赖 Service，符合依赖方向（上层依赖下层）
   - Service 不依赖 Web，避免循环依赖

3. **易于测试**：
   - Service 模块不包含运行时依赖，可以独立进行单元测试
   - Web 模块包含所有依赖，可以进行集成测试

4. **易于维护**：
   - 各模块职责明确，便于维护和扩展
   - 业务逻辑和运行时配置分离

5. **符合规范**：
   - 符合 Spring Boot 和 Dubbo 的最佳实践
   - 符合分层架构设计原则

## 注意事项

1. **Controller 位置**：
   - Provider 如果有 HTTP 接口，Controller 放在 `provider-web` 模块
   - Consumer 的 Controller 放在 `consumer-web` 模块

2. **启动类位置**：
   - Provider 启动类在 `provider-service` 模块
   - Consumer 启动类在 `consumer-service` 模块

3. **配置文件位置**：
   - 配置文件都在各自的 `service` 模块中
   - 因为启动类在 service 模块，配置文件需要和启动类在一起

4. **包扫描**：
   - 确保启动类能够扫描到所有需要的组件
   - 如果包结构不同，需要配置 `@ComponentScan`
