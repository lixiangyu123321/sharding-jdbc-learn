# CSRF攻击：跨站请求伪造完全解析
CSRF（Cross-Site Request Forgery，跨站请求伪造，也常写作XSRF），简单说就是**攻击者利用用户已登录的合法身份，在用户不知情的情况下，伪造用户的操作请求发送给目标网站，让目标网站误以为是用户本人发起的操作，从而执行非用户意愿的行为**。

形象点类比：你刚打开家门（登录目标网站，持有合法会话），还没拔钥匙（浏览器保留登录态），攻击者趁你不注意，从你家门口的门缝里伸手，用你的钥匙按了家里的开关（伪造请求）—— 家里的电器（目标网站）只认钥匙（登录态），不会管是谁按的开关，最终执行了攻击者想要的操作。

### 核心前提：CSRF攻击的3个必要条件
攻击者要成功实施CSRF，必须同时满足这3点，缺一不可：
1. **用户已登录目标网站**：目标网站为用户创建了会话，浏览器保存了登录态（如SessionID的Cookie、登录令牌等），且会话未过期；
2. **用户在登录态下，访问了攻击者的恶意网站/点击了恶意链接**：这是攻击者发起伪造请求的触发条件；
3. **目标网站的操作请求**：**未做CSRF防御**，仅通过浏览器自动携带的登录态验证身份，不校验请求的「真实性」（即是否是用户主动发起）。

### 核心本质：利用HTTP的无状态+浏览器的「自动携带Cookie」特性
CSRF的核心漏洞，并非攻击者破解了用户的密码，也不是窃取了用户的登录信息，而是利用了**浏览器的一个默认行为**：**当用户访问某个域名的请求时，浏览器会自动将该域名下的所有有效Cookie（包括登录态的SessionID、认证令牌）一起发送给服务器**，且这个过程是**无感知、自动完成**的。

攻击者正是利用了这个特性：不需要获取用户的Cookie内容，只需要诱导已登录的用户，在浏览器中发起一个指向目标网站的请求—— 浏览器会自动带上目标网站的登录Cookie，目标网站验证Cookie合法后，就会执行该请求。

### 一个最经典的CSRF攻击场景（转账案例）
假设某银行网站有一个转账接口，通过POST请求实现，仅验证用户的登录Cookie，无任何CSRF防御：
```
# 银行转账接口：向指定账户转指定金额，仅验证登录态
POST https://bank.com/transfer
参数：toAccount=攻击者账户&money=1000
```
#### 攻击步骤：
1. 你登录了银行网站（`bank.com`），完成操作后没有登出，浏览器保留了`bank.com`的登录Cookie；
2. 你在未关闭浏览器的情况下，随手点开了攻击者发来的恶意网站`evil.com`；
3. 恶意网站的页面中，隐藏了一段自动执行的代码（如表单自动提交、JS请求），代码的作用就是**向`bank.com/transfer`发送伪造的转账请求**，参数是攻击者的账户和转账金额；
4. 你的浏览器发起这个请求时，会**自动携带`bank.com`的登录Cookie**，发送给银行服务器；
5. 银行服务器验证Cookie合法，确认是「已登录的你」发起的请求，于是执行转账操作—— 你在完全不知情的情况下，钱被转走了。

#### 关键点：你从未在恶意网站输入过银行的账号密码，攻击者也没窃取你的Cookie，只是「借了你的身份」。

### CSRF攻击的典型危害
根据目标网站的操作权限，CSRF的危害可轻可重，常见场景包括：
- 非敏感操作：修改用户的昵称、头像、个性签名等；
- 敏感操作：转账、消费、修改密码/绑定手机/收货地址、发布不良内容、删除数据、关注/拉黑他人等；
- 极端场景：若用户是网站管理员，攻击者可通过CSRF伪造管理员请求，实现后台数据篡改、服务器权限操作等，危害整个网站。

### 容易混淆的点：CSRF和XSS的核心区别
很多人会把CSRF和XSS（跨站脚本攻击）弄混，两者都是针对Web网站的攻击，但**本质、手段、防御思路完全不同**，核心区别看下表：

| 特性         | CSRF（跨站请求伪造）| XSS（跨站脚本攻击）|
|--------------|---------------------------------------------|---------------------------------------------|
| 核心目的     | 伪造用户请求，**借用户身份执行操作**         | 向目标网站注入恶意脚本，**窃取/控制用户数据** |
| 关键手段     | 利用浏览器自动携带Cookie的特性，无数据窃取   | 注入JS/VBS等脚本，在用户浏览器执行          |
| 数据流向     | 攻击者→伪造请求→目标网站（无用户数据泄露）| 目标网站→恶意脚本→窃取用户数据→攻击者        |
| 依赖条件     | 目标网站无CSRF防御，用户保持登录态           | 目标网站无XSS防御（如未过滤用户输入）|
| 防御核心     | 校验请求的「真实性」（如同步令牌、SameSite） | 过滤/转义用户输入，禁止未授权脚本执行（如CSP）|

**一句话总结**：**XSS是「偷」用户的身份/数据，CSRF是「借」用户的身份做事**；且XSS能绕过CSRF防御（比如通过XSS窃取CSRF令牌，再伪造带令牌的请求），因此防御时需要两者结合。

### 常见的CSRF攻击类型
根据请求的发起方式，CSRF主要分3类，其中**GET型最易实现，POST型危害更大**：
1. **GET型CSRF**：利用GET请求发起，攻击者只需构造一个恶意链接/图片标签，用户点击/加载后就会触发，比如：
   ```html
   <!-- 恶意网站中的图片标签，加载时自动发起GET请求 -->
   <img src="https://bank.com/transfer?toAccount=123&money=1000" style="display:none" />
   ```
   特点：实现简单，无需用户交互（图片自动加载），但部分网站的敏感操作会限制为POST请求，可规避此类攻击。

2. **POST型CSRF**：利用POST请求发起，攻击者需要在恶意网站中构造一个隐藏的表单，并通过JS自动提交，比如：
   ```html
   <!-- 恶意网站中的隐藏表单，页面加载后自动提交POST请求 -->
   <form action="https://bank.com/transfer" method="post" id="csrfForm">
       <input type="hidden" name="toAccount" value="123" />
       <input type="hidden" name="money" value="1000" />
   </form>
   <script>document.getElementById('csrfForm').submit();</script>
   ```
   特点：针对网站的敏感POST操作（转账、修改信息），危害更大，也是防御的重点。

3. **AJAX型CSRF**：利用JS的AJAX/Fetch发起跨域请求，原理和POST型一致，但部分浏览器的**跨域策略（CORS）** 会限制此类请求，因此攻击者通常会结合其他漏洞绕过（如目标网站的CORS配置不当）。

### 为什么CSRF攻击无法窃取用户的Cookie？
这是很多人的核心疑问：攻击者既然能利用Cookie，为什么不直接窃取？
答案是**浏览器的同源策略（Same-Origin Policy）** 保护了Cookie：
- 同源策略规定：**A域名的页面，无法通过JS读取/修改B域名的Cookie、DOM、数据等**；
- 攻击者的恶意网站`evil.com`，无法通过任何脚本获取到你浏览器中`bank.com`的Cookie内容，只能诱导浏览器**自动携带**Cookie发送请求，而无法查看Cookie的具体值。

简单说：攻击者只能「用」你的Cookie，不能「看」你的Cookie—— 这也是CSRF和XSS的核心区别（XSS能突破同源策略，读取Cookie）。

### 如何快速判断网站是否存在CSRF漏洞？
可以通过「**删除请求的Referer头+保留登录Cookie**」的方式简单测试，核心步骤：
1. 登录目标网站，找到一个敏感操作（如修改密码、发布内容），抓包获取该操作的请求（POST/GET）；
2. 保留请求中的所有参数和登录Cookie，**删除请求头中的Referer字段**（Referer表示请求的来源）；
3. 重新发送该请求，若目标网站仍能成功执行操作，说明**未做CSRF防御**，存在漏洞；
4. 若发送后提示「请求非法」「验证失败」，说明网站做了CSRF防御（如令牌校验、Referer校验）。

### 核心防御方案（按优先级排序）
CSRF的防御核心是**让目标网站能识别出「请求是否是用户主动发起的」**，而非简单验证登录态，主流方案按安全性/通用性排序如下：
1. **同步令牌模式（Synchronizer Token）**：**首选核心方案**，也是最彻底的防御方式（即我们之前聊的，为每个用户会话生成唯一CSRF令牌，请求中携带令牌并由服务端校验）；
2. **SameSite Cookie 属性**：辅助防御，给登录态的Cookie设置`SameSite=Strict/Lax`，限制浏览器跨域携带Cookie（`Strict`表示完全禁止跨域携带，`Lax`表示允许部分安全的跨域携带）；
3. **Referer/Origin 校验**：验证请求的来源域名，仅允许目标网站自身/可信域名的请求，实现简单但有漏洞（Referer可被伪造/屏蔽）；
4. **请求方法限制**：所有敏感操作**禁止使用GET请求**，统一使用POST请求（能规避简单的GET型CSRF，但无法防御POST型）；
5. **二次验证**：对高风险操作（如转账、修改密码），增加**验证码、短信验证、密码再次验证**，即使请求被伪造，也因缺少二次验证信息而无法执行。

**最佳实践**：**同步令牌模式 + SameSite Cookie** 双重防御，兼顾安全性和兼容性，几乎能抵御所有CSRF攻击。

### 总结
CSRF攻击的核心可以用3句话概括：
1. **身份盗用**：利用用户的合法登录态，而非破解/窃取账号密码；
2. **无感知执行**：用户在不知情的情况下，被诱导发起伪造请求；
3. **防御核心**：让网站能区分「用户主动请求」和「攻击者伪造请求」，而非仅验证登录态。

它是Web开发中最常见的安全漏洞之一，尤其是对有用户体系、敏感操作的网站（电商、金融、后台管理系统），**必须做针对性防御**，而同步令牌模式就是解决这个问题的标准方案。
