这句话的核心是讲**Spring Security默认的CSRF令牌仓库`HttpSessionCsrfTokenRepository`的两个核心规则**——也是你使用默认CSRF防护时，前端和后端的「约定规则」，简单说就是：**服务端把要校验的「预期CSRF令牌」存在`HttpSession`里（不用你写任何代码），同时前端携带的「实际CSRF令牌」，只要放在`X-CSRF-TOKEN`请求头里，或者`_csrf`请求参数里，服务端就能自动读取并做对比校验**。

结合之前的同步令牌模式核心逻辑，我把这两句话拆成**「存储规则」和「读取规则」** 两部分，用通俗的语言+实际请求示例讲清楚，你就能直接对应开发中的使用场景。

### 第一部分：「将预期的 CSRF 令牌存储在 HttpSession 中，因此无需额外代码」
这是**服务端侧的规则**，讲的是「服务端生成的、用来做对比的「预期令牌」存在哪，怎么管理」，核心是**框架全自动处理，你不用写任何生成、存储的代码**，对应细节如下：
1. **自动生成+存储**：当用户首次发起请求（如访问服务端渲染页面、调用接口），Spring Security会自动生成一个UUID格式的CSRF令牌，通过`HttpSessionCsrfTokenRepository`直接存入当前用户的**专属HttpSession**中（Session是用户级的，每个用户的令牌相互独立）；
2. **无需额外代码**：你不用像手动实现那样，写工具类生成UUID、调用`session.setAttribute()`存令牌，框架全帮你做了，开启CSRF防护（默认开启）就生效；
3. **预期令牌的作用**：后续前端发起POST/PUT/DELETE等修改类请求时，服务端会从当前用户的Session中取出这个「预期令牌」，作为校验的「标准答案」。

**简单类比**：就像你去银行办业务，银行会给你一个「专属取号单（预期令牌）」，并把这个取号单存在银行的「你的专属档案（Session）」里，不用你自己保管，银行全程帮你存着。

### 第二部分：「从名为 X-CSRF-TOKEN 的 HTTP 请求 header 或默认的请求参数 _csrf 中读取令牌」
这是**前后端的约定规则**，讲的是「前端拿到令牌后，要放在请求的哪个位置，服务端才能识别并读取到「实际令牌」」，核心是**二选一即可，框架会自动按「先请求头、后请求参数」的顺序读取**，对应细节如下：
1. **读取顺序**：服务端会**优先从请求头`X-CSRF-TOKEN`中读取**，如果没读到，再从**请求参数`_csrf`中读取**，只要其中一个有正确的令牌，就能通过校验；
2. **无需手动写读取代码**：框架的内置CSRF拦截器会自动执行这个读取逻辑，你不用像手动实现那样写`getCsrfTokenFromRequest`工具类，框架全帮你做了；
3. **实际令牌的作用**：前端携带的这个令牌，就是服务端要和「Session中的预期令牌」做对比的「答题纸」，两者一致才认定请求合法。

**简单类比**：银行叫号时，你只要把「取号单（实际令牌）」**要么交给窗口柜员（请求头`X-CSRF-TOKEN`），要么放在窗口的指定卡槽（请求参数`_csrf`）**，柜员都能拿到并和银行档案里的取号单对比，二选一就行。

## 结合实际请求示例，看清楚两种携带方式（最直观）
假设服务端生成的CSRF令牌值是`6a8b9c7d-1e2f-3g4h-5i6j-7k8l9m0n1o2p`，并存入了用户Session，下面两种请求方式服务端都能正常读取令牌并校验。

### 方式1：令牌放在请求头「X-CSRF-TOKEN」中（推荐，适配前后端分离/JSON请求体）
适合Vue/React等前后端分离项目，或服务端渲染中的AJAX请求，令牌和业务参数分离，不依赖请求体格式（JSON/表单都能用），也是最通用的方式。
#### 实际HTTP请求示例
```http
# 转账请求：POST（修改状态，需CSRF校验）
POST /bank/transfer HTTP/1.1
Host: localhost:8080
Cookie: JSESSIONID=xxx  # 用户的SessionID，服务端通过它找到Session中的预期令牌
X-CSRF-TOKEN: 6a8b9c7d-1e2f-3g4h-5i6j-7k8l9m0n1o2p  # 令牌放在请求头，框架优先读取
Content-Type: application/json  # 适配JSON请求体（前后端分离主流）

# JSON格式的业务参数，和令牌完全分离
{
  "amount": 100.00,
  "targetAccount": "987654321"
}
```
#### 核心特点
- 令牌在**请求头**，业务参数在**请求体**，相互独立，适配所有请求体类型（JSON/`x-www-form-urlencoded`/`form-data`）；
- 前端只需在AJAX请求中添加一个请求头，无需修改业务参数，代码更整洁；
- 避免令牌出现在URL中，无泄露风险。

### 方式2：令牌放在请求参数「_csrf」中（默认，适配传统表单提交）
适合服务端渲染的传统表单提交（如Thymeleaf/JSP的`<form>`），框架会自动为表单注入`_csrf`隐藏input，提交时令牌会随表单参数一起发送，无需前端写任何JS代码。
#### 实际HTTP请求示例
```http
# 转账请求：POST（修改状态，需CSRF校验）
POST /bank/transfer HTTP/1.1
Host: localhost:8080
Cookie: JSESSIONID=xxx  # 用户的SessionID，服务端通过它找到Session中的预期令牌
Content-Type: application/x-www-form-urlencoded  # 表单默认的请求体类型

# 业务参数 + _csrf请求参数，用&拼接，框架读取_csrf参数值
amount=100.00&targetAccount=987654321&_csrf=6a8b9c7d-1e2f-3g4h-5i6j-7k8l9m0n1o2p
```
#### 核心特点
- 令牌是**普通请求参数**，和业务参数混在一起，仅适用于「键值对型」请求体（`x-www-form-urlencoded`/`form-data`），**不适用JSON请求体**（JSON是层级结构，无法直接放平级的`_csrf`参数）；
- 服务端渲染中，Thymeleaf会**自动为<form>添加`name="_csrf"`的隐藏input**，前端只需提交表单，无需手动处理令牌，零开发成本；
- 这也是你最开始贴的「同步令牌模式官方示例」中使用的方式，和Spring Security默认规则完全一致。

## 关键补充：这两个规则的「适用场景」和「底层逻辑」
### 1. 为什么框架要支持「请求头+请求参数」两种方式？
核心是**兼顾「传统开发场景」和「现代开发场景」**，做到零成本兼容：
- 传统服务端渲染（表单提交）：用`_csrf`请求参数，框架自动注入，前端零代码；
- 现代前后端分离（AJAX/JSON）：用`X-CSRF-TOKEN`请求头，适配JSON请求体，代码更灵活；
  框架不用你做任何配置，就能同时支持两种场景，这也是Spring Security的封装优势。

### 2. 服务端怎么「关联」「预期令牌」和「实际令牌」？
核心是**通过`JSESSIONID` Cookie**，这是整个校验的「纽带」，步骤如下：
1. 前端发起请求时，浏览器会自动携带目标网站的`JSESSIONID` Cookie（用户的会话标识）；
2. 服务端通过`JSESSIONID`找到当前用户的**专属HttpSession**；
3. 从Session中取出「预期令牌」，再从请求头/参数中读取「实际令牌」；
4. 对比两者是否一致，一致则放行，不一致则返回403 Forbidden。

**关键**：令牌是「用户会话级」的，每个用户的Session中都有自己的预期令牌，攻击者无法跨域获取其他用户的令牌，也无法伪造匹配的令牌。

### 3. 为什么GET/OPTIONS请求不用校验令牌？
框架默认遵循「RESTful设计规范」和「CSRF防护的核心原则」：
- GET/OPTIONS/HEAD等请求是**「安全方法」**，仅用于查询数据、预检请求，不会修改服务器状态，即使被伪造，危害也极小；
- POST/PUT/DELETE/PATCH等请求是**「修改方法」**，会修改服务器状态（转账、改密码、删数据），是CSRF攻击的主要目标，因此强制校验令牌；
  这样设计既保证了核心功能的安全，又兼顾了可用性（比如允许外部网站链接到你的网站查数据）。

## 总结：一句话讲透整句话的意思
使用`HttpSessionCsrfTokenRepository`（Spring Security默认）时，**你不用写任何生成、存储、读取CSRF令牌的代码**，框架会自动把「要校验的预期令牌」存在用户的HttpSession里，同时前端只要把「实际令牌」放在`X-CSRF-TOKEN`请求头，或者`_csrf`请求参数里（二选一），框架就会自动读取并和Session中的预期令牌对比，一致则放行请求，不一致则拒绝，以此实现CSRF防护。

### 核心关键点回顾
1. 存储侧：预期令牌存**用户专属HttpSession**，框架全自动，无需额外代码；
2. 读取侧：实际令牌读**请求头`X-CSRF-TOKEN`（优先）** 或**请求参数`_csrf`**，二选一即可；
3. 关联侧：通过`JSESSIONID` Cookie关联用户的Session，实现「预期令牌-实际令牌」的一对一对比；
4. 场景侧：请求头方式适配前后端分离/JSON，请求参数方式适配传统表单提交，框架零配置兼容。
