你想知道`HttpSession`会话过期的含义，简单来说，**HttpSession会话过期就是服务器为用户创建的「专属会话」，在指定时间内没有任何交互操作后，被服务器主动销毁、失效的过程**；过期后，会话中存储的用户信息（比如登录态、临时数据）会被清空，用户若继续操作系统，服务器会重新创建一个全新的空会话。

这个概念是基于**B/S架构（浏览器/服务器）** 设计的——HTTP协议本身是**无状态**的（服务器不会记住每次请求的用户身份），所以Servlet容器（Tomcat、Jetty等）通过`HttpSession`为每个用户创建**专属的临时会话**，用来存储用户的登录状态、页面临时数据等，而「会话过期」就是服务器为了节省内存、保证安全，对长期闲置的会话做的**自动清理机制**。

### 一、用通俗的例子理解：像超市的储物柜
把`HttpSession`比作超市的**电子储物柜**：
1. 你第一次进入超市（首次访问系统），服务器给你开一个专属储物柜（创建`HttpSession`），生成唯一的柜门密码（JSESSIONID，存在浏览器Cookie中）；
2. 你购物过程中，随时打开柜门存取东西（浏览器每次请求都会携带JSESSIONID，服务器通过它找到你的会话，读取/修改会话中的数据，比如保存你的登录名）；
3. 若你**长时间不碰储物柜**（比如离开超市忘了关，超过超市规定的闲置时间），超市工作人员会**清空储物柜并收回**（服务器销毁会话，即「会话过期」）；
4. 过期后你再回来想打开柜门（继续操作系统），密码已经失效，工作人员会给你开一个**全新的空储物柜**（服务器创建新的`HttpSession`），之前存的东西（登录态、临时数据）全都没了。

### 二、会话过期的两个核心触发条件
Servlet容器中`HttpSession`的过期，核心由**「闲置超时时间」** 控制，有两种常见触发方式（效果一致）：
#### 1. 容器默认的闲置超时（最常用）
Tomcat等Servlet容器**默认的会话闲置超时时间是30分钟**——从用户的**最后一次请求**开始计时，若接下来30分钟内，用户没有对服务器发起任何请求（无交互），服务器就会自动销毁该用户的`HttpSession`。
- 注意：**用户的每次有效请求（GET/POST等）都会重置超时计时器**（比如30分钟超时，用户20分钟时刷新了页面，计时器会重新从0开始算30分钟）；
- 仅**闲置时间**达到阈值才会过期，用户正常操作时会话永远不会过期。

#### 2. 手动配置超时时间（开发中常用）
可通过代码、配置文件自定义超时时间，覆盖容器默认的30分钟，单位是**分钟**。
##### 方式1：代码中动态配置（针对单个会话/全局）
```java
// 在Servlet/Controller中，获取当前用户的HttpSession
HttpSession session = request.getSession();
// 设置当前会话的闲置超时时间为15分钟（-1表示永不过期，不推荐）
session.setMaxInactiveInterval(15);

// 若想全局配置，可在Web应用的初始化类中设置，或用方式2
```
##### 方式2：web.xml中全局配置（Servlet传统方式）
```xml
<!-- 全局配置所有HttpSession的闲置超时时间为20分钟 -->
<session-config>
    <session-timeout>20</session-timeout>
</session-config>
```
##### 方式3：Spring Boot中配置（更简洁，推荐）
在`application.properties/application.yml`中配置，底层还是对接Servlet容器的超时机制：
```properties
# Spring Boot配置会话超时，单位：秒（注意：这里是秒，和原生Servlet的分钟不同！）
# 配置30分钟超时：30*60=1800秒
server.servlet.session.timeout=1800
```

### 三、会话过期后，用户的直观感受
会话过期后，用户继续操作系统，会出现**最典型的两个现象**，也是开发中最常遇到的场景：
1. **登录态丢失**：原本已登录的用户，会被跳转到登录页面，需要重新登录（因为登录态一般存在`HttpSession`中，会话销毁后登录态也没了）；
2. **会话中的临时数据丢失**：比如用户在购物车中添加的商品、表单中未提交的临时数据，若存在`HttpSession`中，过期后会全部清空。

### 四、和「浏览器Cookie过期」的区别（易混淆点）
很多人会把`HttpSession`过期和Cookie过期搞混，因为两者都和登录态相关，但**本质是两个层面的东西**，核心区别如下：
| 对比项 | HttpSession会话过期 | 浏览器Cookie过期 |
|--------|---------------------|------------------|
| 存储位置 | **服务器端**（内存/持久化） | **客户端浏览器**（本地文件） |
| 核心标识 | JSESSIONID（会话ID，存在Cookie中） | 就是Cookie本身（比如存储的token、用户信息） |
| 过期结果 | 服务器销毁会话，清空会话内所有数据；JSESSIONID失效 | 浏览器删除本地的Cookie文件，不再携带该Cookie发起请求 |
| 登录态丢失原因 | 服务器端没有登录态了，即使浏览器携带旧JSESSIONID，服务器也不识别 | 浏览器不携带JSESSIONID/登录Cookie，服务器找不到对应的会话/登录态 |

**补充**：默认情况下，存储JSESSIONID的Cookie是**会话级Cookie**（浏览器关闭即消失），这也是为什么「关闭浏览器再打开，需要重新登录」的原因——并非`HttpSession`过期了，而是浏览器丢了JSESSIONID，服务器无法找到对应的会话。

### 五、开发中关于会话过期的常见处理场景
#### 1. 给用户友好的过期提示
会话过期后，若直接跳转到登录页，用户可能会困惑，建议在跳转时添加提示：
- 比如登录页显示「您的登录状态已过期，请重新登录」；
- 前后端分离项目中，接口返回统一的状态码（如401 Unauthorized），前端接收到后弹出提示并跳转到登录页。

#### 2. 避免重要操作因过期中断
对于需要长时间操作的页面（比如后台管理系统的表单编辑、电商的下单页面），可做**会话保活**处理：
- 通过**前端定时发AJAX请求**（比如每隔10分钟发一次空请求），重置服务器的会话超时计时器，避免会话过期；
- 示例（jQuery）：
  ```javascript
  // 每隔10分钟发一次GET请求到保活接口，保持会话有效
  setInterval(function() {
      $.get("/keepalive");
  }, 10 * 60 * 1000);
  ```
- 后端只需写一个空的保活接口，无需处理逻辑，仅用于触发会话计时器重置即可。

#### 3. 永不过期的坑（绝对不推荐）
若将超时时间设为`-1`（`session.setMaxInactiveInterval(-1)`），表示会话**永不过期**，这会导致：
- 服务器内存中堆积大量闲置会话，**内存泄漏**，最终服务器崩溃；
- 若用户量较大，短时间内就会耗尽服务器内存，生产环境**严禁使用**。

#### 4. 会话过期后的重定向配置（Spring Security中）
在Spring Security中，若会话过期后用户访问受保护的接口，可配置自动跳转到登录页，并携带原请求地址，方便用户登录后返回原页面：
```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            // 其他配置...
            .sessionManagement((session) -> session
                // 配置会话过期后跳转到登录页，携带原请求地址
                .invalidSessionUrl("/login?error=session_expired")
            );
        return http.build();
    }
}
```
前端登录页可通过`error=session_expired`参数，显示「会话过期」的专属提示。

### 六、核心总结
1. `HttpSession`会话过期是**服务器对长期闲置的用户专属会话的自动销毁机制**，目的是节省内存、保证系统安全，解决HTTP无状态的问题；
2. 核心触发条件是**「闲置超时时间」**（默认30分钟），用户每次请求都会重置计时器，仅长期无交互才会过期；
3. 过期后最直观的现象是**登录态丢失、会话内临时数据清空**，用户需要重新登录；
4. 开发中可自定义超时时间、做会话保活，但**严禁设置永不过期**，同时要给用户友好的过期提示；
5. 区别于Cookie过期：会话过期在**服务器端**，Cookie过期在**客户端**，前者是数据被销毁，后者是标识被丢失。
